# LoadAudit AI

**An AI agent that automates 3-way invoice reconciliation for freight brokers** — extracts data from carrier invoices, checks it against the rate confirmation on file, auto-clears clean matches, and drafts a dispute email + routes to a human for anything that doesn't match.

## The problem

Freight brokers manually cross-check every carrier invoice against the rate confirmation, the load tender, and any pre-authorized accessorials before paying it. This takes several minutes per invoice and, industry-wide, 5-10% of invoices contain at least one billing discrepancy (American Shipper 2024 Freight Audit & Payment Benchmark Study). It's one of the highest-cost manual back-office processes in mid-market logistics.

## What this does

1.  **Extract**: pulls structured fields (load ID, carrier, invoice number, linehaul rate, accessorials, POD status) out of raw invoice text. Three extractors, selectable with `LOADAUDIT_EXTRACTOR=auto|claude|ollama|regex`: an LLM (Claude), a local model through Ollama (no API cost, data stays on your machine), or a regex fallback. Extraction never guesses: if a required field is missing or invalid, the invoice is flagged for human review with the reason.
2. **Match** — deterministically checks the invoice against the rate confirmation on file: rate accuracy, accessorial authorization and amount, POD presence, duplicate-invoice pattern.
3. **Decide**: clean matches are auto-approved. Anything that fails a check is flagged with a plain-language reason. Only real billing discrepancies get a drafted dispute email to the carrier. Extraction failures and unmatched loads are routed to internal review instead, because the carrier has not done anything wrong yet.
4. **Alert a human** — flagged invoices are posted to a Slack channel (via an Incoming Webhook) with the discrepancy and the drafted dispute email, so someone can act on it immediately. If no webhook is configured, it logs locally instead, so the rest of the pipeline still works without Slack set up.
5. **Evaluate** — a labeled synthetic dataset + eval harness scores the pipeline's precision/recall, so results are measured honestly rather than asserted.

## Quickstart To use a local model: install [Ollama](https://ollama.com), run `ollama pull qwen2.5:7b`, then `set LOADAUDIT_EXTRACTOR=ollama` (Windows) or `export LOADAUDIT_EXTRACTOR=ollama`. Change the model with `OLLAMA_MODEL`.

```bash
git clone <your-repo-url>
cd loadaudit-ai
pip install -r requirements.txt

# 1. generate the synthetic dataset (30 loads, ~30% with a deliberate discrepancy)
python data/generate_synthetic_data.py

# 2. run the evaluation harness
python -m eval.run_eval

# 3. run the API and try it yourself
uvicorn src.api:app --reload
# then POST to http://127.0.0.1:8000/invoices/audit or /invoices/audit/raw
```

Set ollama model in your environment to use LLM-based extraction on raw invoice text; without it, `src/extraction.py` falls back to a regex parser so the whole pipeline still runs.

Set `SLACK_WEBHOOK_URL` (from a Slack Incoming Webhook — see api.slack.com/apps) to actually post flagged invoices to a channel; without it, alerts are printed to the console instead.

## Evaluation results

**Synthetic dataset (30 invoices):** 100% accuracy, precision and recall. This is expected on clean, generated data. It is not evidence of real-world performance.

**Stress test on messy invoices.** To find out what breaks, I wrote deliberately messy fake invoices (all names and amounts are invented): different wording for the same field, a missing rate, "POD to follow", charges billed by the hour, scanner typos, and forwarded emails. Run them with `python messy_files.py create` then `python messy_files.py run`, or compare extractors with `python compare_extractors.py`.

My first version scored **5 of 12** on the first messy set:
- 4 invoices crashed the API because a field could not be read.
- 2 bad invoices were wrongly **auto-cleared** (a "POD to follow" invoice and an hourly detention overcharge). These are the dangerous failures.

After fixes (flag unreadable invoices for human review instead of crashing, strict proof-of-delivery wording, more flexible parsing):

| Extractor | Messy set (12) | Held-out set (8) | Bad invoices wrongly cleared |
|---|---|---|---|
| Regex | 12/12 | 6/8 | 0 |
| Ollama qwen2.5:7b | _fill in_ | _fill in_ | _fill in_ |

The messy set was used to tune the regex fixes, so 12/12 overstates real performance. The held-out set of 8 was written without tuning, and 6/8 is the more honest number. Both misses were clean invoices sent to human review, which is the safe direction.

**Not yet tested:** real invoices from a freight broker, scanned PDFs, or the Claude extraction path on this messy set.

These numbers are on a synthetic, labeled test set generated by `data/generate_synthetic_data.py` — see [docs/architecture.md](docs/architecture.md) for why this is expected on synthetic data and what the real bottleneck (extraction quality on messy real-world documents) looks like in production.
